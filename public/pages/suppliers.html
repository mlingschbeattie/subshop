What is SSRF?

Server-Side Request Forgery (SSRF) occurs when an application fetches a remote resource using a URL supplied by the user — without validating that URL against an allowlist.

An attacker can redirect the server to:

  • Internal services (http://localhost:6379 — Redis)
  • Cloud metadata APIs (http://169.254.169.254/)
  • Private network hosts
  • Local files via file:///etc/passwd

Payloads to Try

Vulnerable Code

The core SSRF flaw — user URL passed directly to fetch(): 

// VULNERABILITY: No URL validation — user controls the target
async function checkSupplier() {
  const url = document.getElementById('supplier-url').value;
  // No allowlist check — any URL accepted
  const response = await fetch(url);
  const text = await response.text();
  displayOutput(text);
}

Fix: Validate the URL against a strict allowlist of known supplier domains before fetching. Reject private IPs, localhost, and non-HTTPS schemes at the server layer.

🦆

When a server fetches URLs on behalf of users, attackers can redirect it to internal systems. The server has access to internal network resources the attacker can't reach directly.

Think of it like: Tricking someone's assistant into calling your competitors and reading back the answers.

Real world: 2019 Capital One breach — SSRF via misconfigured AWS metadata endpoint exposed 100M records.
